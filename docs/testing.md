# Как гонять проверки

Проверок в `scripts/` шесть десятков, и почти все — браузерные: поднимают
приложение и утверждают что-то про его поведение. Здесь то, что нужно знать до
первого запуска, и одно правило, которое стоит часа потерянного времени.

## Правило первое: вывод сохраняется в файл

**Никогда не пропускайте прогон через `| tail` или `| head`.**

Итог печатается ПЕРЕД подробностями по упавшим проверкам — так удобнее читать с
экрана. Значит `| tail -60` срезает ровно итог и оставляет хвост подробностей, а
`| head` — наоборот. Часовой прогон при этом придётся повторить целиком.

Хуже того: **через трубу теряется код возврата**. `cmd | tail` возвращает код
`tail`, а он успешен всегда. Упавший прогон при этом выглядит зелёным — так один
прогон Playwright (12 упавших испытаний из 18) был здесь объявлен успешным, и
неправда продержалась до тех пор, пока не всплыл `e2e/test-results/.last-run.json`
со списком упавших. Если труба всё же нужна — берите код первого звена:

```
cmd > /tmp/run.log 2>&1; echo "код $?"        # так правильно
cmd | tail -20; echo "код ${PIPESTATUS[0]}"   # так тоже, но легко забыть
```

Прогон регрессии пишет лог сам:

```
node scripts/run-regression.mjs          # → regression-local-20260830-142530.log
DEV=1 node scripts/run-regression.mjs    # → regression-dev-…log
```

Имя лога — со временем запуска, и печатается первой строкой. Постоянное имя
подводит: пока идёт сборка, в файле лежит ПРОШЛЫЙ итог, и его легко принять за
сегодняшний. Своё имя задаётся через `LOG=`.

В логе — полный вывод КАЖДОЙ проверки, не только упавшей. На экран идёт короткая
сводка. Отдельную проверку перенаправляйте руками:

```
node scripts/check-curator-flow.mjs > /tmp/curator.log 2>&1; echo "код $?"
```

Дальше по файлу работайте `grep`, а не чтением целиком: в логе десятки тысяч
строк, и открывать его весь — это просто время и деньги, потраченные на прокрутку.

```
grep -E "^(OK|FAIL)" regression-local-*.log   # сводка
sed -n '/═══ check-fiber-week/,/═══/p' regression-local-*.log   # одна проверка
```

Это же относится к долгим прогонам вообще: запускайте в фоне с перенаправлением в
файл, а не держите вывод в терминале.

## Быстрее всего — не гонять всё

Полный прогон нужен ровно в одном месте: в конце, чтобы поймать задетое соседнее.
Пока чинишь — гоняйте по одной, это 10–60 секунд:

```
DEV=1 node scripts/run-regression.mjs iron-week      # одна (совпадение по имени)
FAILED=regression-dev-….log node scripts/run-regression.mjs   # только упавшее в прошлый раз
ONLY=check-a.mjs,check-b.mjs node scripts/run-regression.mjs  # именной список
```

Полный прогон идёт ЧЕТВЁРКАМИ и занимает около восьми минут (по одной было
тридцать). Мешать друг другу проверкам нечем: у каждой свой браузер, своя база и
свой пользователь на dev-воркерах.

Проверки, которые ЖДУТ МОДЕЛЬ (`*-reask`, `check-fats-retry-gate`,
`check-calcium-iron-reset`, `check-fat-reset`), идут по ОДНОЙ на своей дорожке:
очередь к модели общая, и вчетвером они друг друга топят — падают с «стало
undefined», хотя приложение ни при чём. Остальные в это время идут своим чередом.

Две из них — `check-calcium-iron-reset` и `check-heme-reask` — всё равно иногда не
дожидаются ответа за свои четыре минуты (`WAIT_MS=`). Это про модель, а не про
приложение: перегнать по одной (`ONLY=`) — и они зелёные. По выкладке проходят.

**Выше четырёх не поднимайте.** Проверено: на восьми три проверки развалились —
`check-calcium-iron-reset`, `check-processed-meat-reask`, `check-tg-fallback`.
Все три ждут фиксированными паузами (`waitForTimeout`), и под нагрузкой пауза
перестаёт покрывать то, что за ней должно успеть: миграцию, ответ фонового
прохода. Это же объясняет одиночные «необъяснимые» падения — они случаются, когда
рядом идёт другой прогон. `JOBS=1` возвращает прежний порядок по одной.

## Как проверки устроены

Две породы, и различать их важно.

**Со своим сервером** — `check-curator-flow`, `check-fresh-bind-unbind`,
`check-planka-sync`, `check-diary-week`. Поднимают локальный сервер сами
(`scripts/lib/devserver.mjs`), запускаются просто:

```
node scripts/check-curator-flow.mjs
DEV=1 node scripts/check-curator-flow.mjs   # по ВЫКАЧЕННОМУ приложению
```

**Накопленные** — остальные. Ждут адрес в `FE` и браузер по умолчанию. Их гоняет
`run-regression.mjs`, который подставляет им общий сервер и установленный
chromium.

## Почему нужен локальный сервер

В части окружений (в том числе в контейнере, где это писалось) **браузер наружу
не ходит, а node ходит**. Поэтому `devserver.mjs` раздаёт статику и проксирует
обращения приложения к живым dev-воркерам: браузер знает только `127.0.0.1`, а до
воркеров дотягивается node.

`DEV=1` меняет источник статики: файлы берутся с выкаченного приложения, а не из
локального `dist`. Тогда проверка захватывает и саму выкладку — заголовки,
`_worker.js`, пути к картинкам. Адреса воркеров подменяются в обоих случаях:
настоящие приложению отдать нельзя, оно до них не дойдёт.

## Что этим НЕ покрыто

Стоит помнить, чтобы не обещать лишнего:

- **Service worker выключен** во всех прогонах — путь обновления PWA не
  проверяется.
- **CORS живого происхождения** не проверяется: запросы идут через локальный
  прокси. Именно этот класс ошибки однажды ловился руками, запросом `OPTIONS`.
- **Апгрейд базы** — проверки СТАВЯТ номер версии в `db_schema_version` и тем
  запускают миграции, но базу, СОЗДАННУЮ старой сборкой, никто не открывает. То,
  что `idb` сносит необъявленные сторы при открытии, этим не ловится.
- **Настоящее происхождение** — по локальной сборке `_worker.js` не исполняется
  вовсе, поэтому три проверки (перехват браузера, персональный манифест) там
  пропускаются: `DEV=1` для них обязателен.

## Стенд и его ограничения

`scripts/harness.mjs` сеет пользователя с НЕНАСТОЯЩИМ токеном: приложение с ним
не сможет ни синхронизироваться, ни спросить сервер о кураторе. Поэтому стенд
сразу проставляет `support_current_peer` — иначе недельный пересчёт планок не
запускается вовсе: он ждёт ответа, кто ведёт этого человека.

Проверкам, которым нужен настоящий счёт, его выдаёт `scripts/lib/devuser.mjs`
(`createPaidUser`, `mintToken`) — тем же секретом, что у dev-воркеров. Это и есть
«обход авторизации»: паскей проверяет личность, а проверкам нужна не она, а всё,
что происходит после входа.

## Когда проверка упала

Прежде чем чинить приложение — убедитесь, что упала не сама проверка:

1. **Может ли она вообще работать здесь?** Часть скриптов ходит в админку на
   другом происхождении или вшила живой адрес. Такие честно называются в
   пропусках `run-regression.mjs`, с причиной у каждого.
2. **Это уже было?** Соберите `main` в отдельном дереве и прогоните тот же
   список: разница двух логов и есть то, что сломано вами.

   ```
   git worktree add /tmp/main-tree origin/main
   cd /tmp/main-tree/frontend && trunk build --release
   FE_DIST=/tmp/main-tree/frontend/dist node scripts/run-regression.mjs
   ```
3. **Что говорит само приложение?** Оно называет причины вслух: «пересчёта нет —
   адресат ещё не известен», «планка ещё не поставлена». Ловите их через
   `page.on('console')` — это быстрее любого разглядывания кода.

## Чем локальный сервер отличается от выкладки — и как из-за этого врут проверки

Разбор всех падений (август 2026) показал: две трети из них были не о приложении,
а о том, что проверка не узнавала себя в нашем окружении. Отличия ровно четыре, и
каждое стоило по несколько проверок.

**1. Адрес воркера — не адрес воркера.** Приложение зовёт `/api/ai/…`,
`/api/sync/…`, а не `ai-worker-dev…`. Всё, что цепляется за ИМЯ воркера, мимо:
`page.route(/ai-worker/)` не перехватит подменённый ответ, `ctx.route(SYNC)` не
перекроет синк, счётчик запросов «к модели» насчитает ноль. Ловите оба вида:

```js
page.route((u) => /\/chat\/completions/.test(String(u))
  && /ai-worker|\/api\/ai\//.test(String(u)), stub);
```

**2. Браузер, которым пришли, доезжает до `_worker.js`.** Сервер передаёт
`User-Agent` наверх, и выкладка отвечает по-разному: Mi Browser получает свою
страницу вместо приложения, Яндекс — свою. Заодно это значит, что **окна
телефонного размера мало**: без телефонного `User-Agent` экран установки уходит в
ДЕСКТОПНУЮ ветку, где вместо инструкции стоит «приложение предназначено для
мобильных устройств». Берите `devices["iPhone 13"]`, а не только `viewport`.

**3. Происхождение страницы — `127.0.0.1`.** `Origin` передаётся (без него
auth-воркер отвечает «missing ceremony origin» и вход не начинается), но `rpId`
ключа-паспорта привязан к настоящему домену. Значит вход по ключу здесь
непроверяем в принципе — это не поломка окружения, а смысл привязки.

**4. Конфигурация берётся у выкладки.** `config/frontend.toml` отдаётся её же, и
переписываются только адреса воркеров. Всё остальное — модели опознания, ссылка
на бота оплаты — то же, что у людей.

## Три ведра, по которым раскладывается падение

1. **Устаревший сид или ожидание.** Самое частое. Продукт поменялся, проверка —
   нет. Признаки: пустые панели, прочерки вместо чисел, «планка не изменилась».
   Почти всегда чинится сидом, а не приложением.

   Чаще всего сид не договаривает ровно в двух местах. Оба — ТРЕБОВАНИЯ, а не
   особенности реализации: приложение ведёт себя правильно, и менять его, чтобы
   проверка позеленела, нельзя.

   - **`planka_history`.** Планка живёт в истории, и она же — цель. День до первой
     установки судить НЕ ПО ЧЕМУ: правила человеку тогда не давали, нарушить он его
     не мог, — поэтому планкой такого дня становится его собственный результат, и
     день засчитывается. Из-за этого сид без истории делает любой день выполненным,
     в том числе день без единого шага. Сеять надо и калорийную планку, и шаговую.
   - **`is_milk_globule`.** «Не знаем» — это не «не глобула». Жир, запертый в
     молочно-жировой глобуле, в баланс не идёт, и продукт без выясненного признака
     из отношения выпадает целиком: шкала честно показывает прочерк вместо числа,
     собранного наполовину.

   Признак того, что вы наткнулись на такое правило, а не на поломку: приложение
   говорит об этом вслух в консоли, а число не «неверное», а ОТСУТСТВУЕТ.

2. **Здесь не запускается.** Другое происхождение, вшитый живой адрес, нужен
   настоящий домен. Такие идут в `SKIP` у `run-regression.mjs` — с причиной,
   названной словами. Молчаливых пропусков быть не должно.

3. **Настоящая ошибка приложения.** Только после того, как первые два исключены.

## Что стоит проверить, прежде чем верить зелёному

- **Жест, а не клик.** Виджет планки открывается парой `pointerdown` +
  `pointerup` на одном месте (`dashboard.rs`, `TAP_SLOP`). Один `pointerup`
  обработчик отбрасывает, и проверка годами мерит пустой экран. Есть
  `tapWidget(page, selector)` в `harness.mjs` — зовите его.
- **Меню строки дневника вызывается кнопкой «⋮»** (`diary-row-menu` →
  `diary-menu-edit`), долгого нажатия больше нет.
- **Фиксированные паузы.** `waitForTimeout(2500)` после открытия формы — это не
  ожидание, а ставка. Ждите появления самих чисел.

## Второй набор: Playwright в `e2e/`

Это ОТДЕЛЬНАЯ порода от всего сказанного выше. `scripts/` поднимает локальный
сервер и ходит через него; `e2e/` гоняет браузер прямо по ВЫКАТКЕ dev
(`https://renorma-fit-dev.pages.dev`). Отсюда и другие грабли.

```
cd e2e
npx playwright test                       # весь набор
npx playwright test lazy-food-flag        # один файл
npx playwright test --repeat-each=3       # проверить устойчивость
```

Никаких дополнительных ключей, переменных и своих конфигураций **не нужно**:
`playwright.config.ts` сам определяет окружение. Что именно он делает и почему —
ниже; знать это надо, только когда что-то пошло не так.

### Браузер берётся из образа

В контейнере агента лежит Chromium 1194, а репозиторный Playwright ждёт свою
сборку и без неё падает ещё до первого теста. Конфигурация подставляет
`/opt/pw-browsers/chromium`, если он есть. **`playwright install` в этом образе
запускать нельзя** — так устроены правила окружения, браузер там уже стоит.

### Наружу — только по TLS 1.2

Если задана `HTTPS_PROXY`, конфигурация добавляет прокси и ключ
`--ssl-version-max=tls1.2`. Без него браузер не открывает НИ ОДНОЙ страницы:
`ERR_CONNECTION_RESET` на любом узле, включая `www.google.com`.

Причина не в TLS 1.3 как таковом, а в размере: приветствие TLS 1.3 у Chromium
весит около 1750 байт, не влезает в один TCP-сегмент, и релей агентского прокси
на нём разваливается. Замерено по вариантам: по умолчанию 1767 B → сброс;
с выключенным постквантовым обменом 1735 B → сброс; TLS 1.2 → код 200. У curl
приветствие втрое короче, поэтому curl через тот же прокси ходит и по TLS 1.3 —
отсюда обманчивое «сеть-то есть, а браузеру её нет».

Проверку сертификатов это не ослабляет: TLS 1.2 проверяет цепочку так же.

### `net::ERR_ABORTED` — почти никогда не про сеть

Аборт означает, что запрос СНЯЛИ, а не что он не дошёл. Чаще всего страницу в
этот момент перезагружает само приложение, и вместе с документом умирают все
запросы в полёте — конфигурация, шрифты, `/health`, все с одной меткой времени.
Прежде чем винить сеть, дёрните тот же адрес из страницы:
`page.evaluate(() => fetch(url))`. Если он отвечает 200 — ищите навигацию.

Так, `page.goto('/onboard')` без `?u=` уводит на «/» (`pages/onboard.rs`), и все
запросы первой страницы обрываются. Это НЕ поломка: настоящая ссылка онбординга
`?u=` несёт, её строит `cloudflare/telegram-worker/src/miniapp.rs`.

### Вход без онбординга: `signInSeeded`

`registerAccount` из `tests/helpers.ts` водит браузер по УСТАРЕВШЕМУ входу
(`/onboard#claim=id.secret`) — приложение такого больше не понимает, обработки
`#claim=` в `pages/onboard.rs` нет вовсе. Всё, что зовёт `registerAccount`, падает
на `onboard-btn-register`; это чинится в испытаниях, а не в приложении.

Пока это не сделано, испытанию, которому нужен просто вошедший человек, годится
`signInSeeded(page, seed)`: сеанс кладётся теми же ключами localStorage, что и при
настоящем входе, подписка с персоной — засевом. Токен заведомо негодный, сервер
отвечает 401 — годится для испытаний про ЭКРАНЫ, не про учётную запись.

### Засев данных: `seedDatabase`

Открывать IndexedDB из испытания бесполезно: миграции на старте перебирают
хранилища и переписывают строки, и записанное испытанием до первой отрисовки не
доживает. Поэтому данные кладутся в localStorage, а раскладывает их САМО
приложение — `frontend/src/services/test_seed.rs`.

Что про это надо знать:

- работает ТОЛЬКО на `renorma-fit-dev.pages.dev`, домен вшит в код;
- засев идёт на запуске, в `lib.rs`: после миграций (иначе не выживет) и до того,
  как приложение решит, что показать (иначе нельзя засеять подписку — а без неё
  экран накрыт оверлеем «проверяем подписку», из-под которого засев и не случался);
- ключ СЪЕДАЕТСЯ: удалили строку, перезагрузили — она осталась удалённой;
- хранилище не из списка `SEEDABLE` — громкая ошибка в консоли, а не тихое ничего.

### Следы прогонов

`e2e/test-results/` не отслеживается (`.gitignore`). Но заглядывать туда полезно:
`.last-run.json` хранит список упавших испытаний последнего запуска, а рядом лежат
`error-context.md` со СНИМКОМ СТРАНИЦЫ на момент падения — по нему сразу видно,
что было на экране вместо ожидаемого.
